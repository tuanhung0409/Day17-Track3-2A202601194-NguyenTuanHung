Multi-Memory Architecture & Logic Guide

🏛️ 4 Tầng Nhớ của Agentic Memory System

💬 Short-Term Working Memory

Vùng nhớ nóng cục bộ của phiên hội thoại hiện tại. Nhanh nhưng giới hạn token.

  • Lưu trữ: In-memory (Sliding Window)
  • Mục đích: Hiểu ngữ cảnh các turn chat gần nhất ("nó", "điều đó").
  • Xử lý áp lực: Compaction + Durable Notes khi vượt ngưỡng.
👤 Long-Term Declarative

Trí nhớ dài hạn bền vững qua nhiều session/thread của từng người dùng cụ thể.

  • Lưu trữ: Zep User Knowledge Graph
  • Mục đích: Nhớ preferences, decisions, open loops/TODOs.
  • Đặc tính: Recency Wins (ưu tiên sở thích mới cập nhật).
📖 Episodic Experience

Lưu vết các quỹ đạo thử nghiệm và kết quả: "lần trước đã làm gì và được gì".

  • Lưu trữ: Zep User Graph (Scope: Episodes)
  • Mục đích: Tránh lặp lại lỗi, tái sử dụng giải pháp đã kiểm chứng.
  • Ví dụ: "Đã thử tăng timeout nhưng fail, connection pool mới work".
📚 Semantic Domain KB

Tri thức miền, quy tắc nghiệp vụ, tài liệu dùng chung toàn hệ thống (không của riêng user nào).

  • Lưu trữ: Standalone Graph (graph_id chung)
  • Mục đích: Tra cứu tài liệu, mã quy tắc (e.g. PAYMENT-RULE-3).
  • Phạm vi: Toàn cục (Global), không theo user_id.

1. retrieve_long_term(self, user_id, thread_id, query) ▼

Mục đích: Lấy Zep Context Block (tổng hợp facts & user state phù hợp nhất với query hiện tại) + trích xuất facts với mốc thời gian/validity range.

src/memory_student.pyPython 3.12
def retrieve_long_term(self, user_id: str, thread_id: str, query: str) -> str:
    # 1. Nạp query vào thread slice để Zep tính toán mức độ liên quan
    prime_eval_thread(self.client, user_id, thread_id, query)
    
    # 2. Lấy Context Block đã được Zep tổng hợp
    user_context = self.client.thread.get_user_context(thread_id=thread_id)
    context_block = getattr(user_context, "context", "") or ""

    # 3. Tìm kiếm thêm các Facts trong Graph (scope='edges') để lấy validity range/audit
    try:
        facts = self.client.graph.search(
            user_id=user_id,
            query=cap_query(query),
            scope="edges",
            limit=20,
        )
        fact_text = render_graph_search(facts)
    except Exception:
        fact_text = ""
        
    # 4. Ghép kết quả Context Block và Fact text
    return join_nonempty([context_block, fact_text], sep="\n\n")

Điểm mấu chốt: Dùng prime_eval_thread trước để Zep Context Block nhận biết câu hỏi hiện tại, từ đó trả về facts có liên quan cao nhất.

2. retrieve_episodic(self, user_id, query) ▼

Mục đích: Truy vấn các bài học/kinh nghiệm trong quá khứ đã được nạp dưới dạng episodes của user.

src/memory_student.pyPython 3.12
def retrieve_episodic(self, user_id: str, query: str) -> str:
    # Tìm kiếm theo user_id với scope="episodes"
    results = self.client.graph.search(
        user_id=user_id,
        query=cap_query(query),
        scope="episodes",
        limit=15,
    )
    # Cắt gọn độ dài mỗi episode (180 ký tự) để không vượt budget
    return render_graph_search(results, episode_char_cap=180)

Điểm mấu chốt: Dùng episode_char_cap=180 giúp giữ được nhiều episodes riêng biệt hơn trong ngân sách token eo hẹp.

3. retrieve_semantic(self, graph_id, query) ▼

Mục đích: Tra cứu tài liệu và quy tắc kỹ thuật chung trên Knowledge Graph độc lập (không dính đến bất kỳ user nào).

src/memory_student.pyPython 3.12
def retrieve_semantic(self, graph_id: str, query: str) -> str:
    q = cap_query(query)
    try:
        # scope="episodes" giữ nguyên các mã code literal như PAYMENT-RULE-3
        results = self.client.graph.search(
            graph_id=graph_id,
            query=q,
            scope="episodes",
            limit=8,
        )
    except Exception:
        # Fallback sang nodes nếu SDK/account không hỗ trợ episodes trên standalone graph
        results = self.client.graph.search(
            graph_id=graph_id,
            query=q,
            scope="nodes",
            limit=8,
        )
    return render_graph_search(results)

Lưu ý: Phải truyền graph_id (ví dụ: vinuni-lab17-domain-kb), tuyệt đối không truyền user_id vào hàm này.

🔄 Cơ Chế Short-Term Memory & Compaction

1

Nhận tin nhắn mới (Chat Turn)

Tin nhắn mới được thêm vào danh sách messages trong ShortTermMemory.

2

Phát hiện áp lực bộ nhớ (Detect Pressure)

Kiểm tra: Số lượng tin nhắn > max_recent_messages (6) HOẶC Tổng token > pressure_tokens (500).

3

Trích xuất ghi chú bền vững (Durable Notes Extraction)

Quét các từ khóa bắt buộc (deadline, todo, constraint, must, REVIEW-DEADLINE-1600) từ các tin nhắn cũ sắp bị xóa để lưu riêng vào durable_notes.

4

Tóm tắt & Cắt trượt (Sliding Window Compaction)

Nén các turn cũ thành đoạn tóm tắt ngắn + giữ nguyên K tin nhắn gần nhất + đính kèm Durable Notes.

💡 Tại sao không dùng Buffer đơn thuần?

Nếu chỉ dùng Buffer (lưu toàn bộ chat history), số lượng token sẽ tăng tuyến tính, làm tràn context window của LLM và gây nhiễu context. Kỹ thuật Sliding Window + Compaction giúp bảo tồn 100% các ràng buộc quan trọng (constraints/deadlines) trong khi giữ lượng token luôn ổn định dưới ngưỡng cho phép.

🛡️ Các Nguyên Lý Cốt Lõi & Phân Bổ Ngân Sách

🕒 Recency Wins (Xử lý xung đột)

Khi người dùng thay đổi quyết định hoặc sở thích (ví dụ: ban đầu chọn Python, sau đó chuyển sang TypeScript + NestJS cho dự án BLUEBIRD-42):

  • Hệ thống ưu tiên thông tin mới nhất cho câu trả lời hiện tại.
  • Dữ liệu cũ vẫn được lưu trữ kèm timestamp/provenance trong Graph để tra cứu lịch sử khi cần.
🔒 User Isolation & Privacy

Đảm bảo tính cô lập dữ liệu tuyệt đối giữa các người dùng:

  • Truy vấn của lan-lab17 không bao giờ được trả về facts của minh-lab17 (tránh data-leak bug).
  • Right to be forgotten: Lệnh src.forget cho phép xóa hoàn toàn dữ liệu của một user mà không ảnh hưởng người khác.

📄 test_short_term.py — Kiểm tra Short-Term Memory & Compaction ▼

Kiểm tra xem cơ chế Sliding Window Compaction có hoạt động đúng không — cụ thể là dù có nhiều turn chat rác vào sau, các constraint quan trọng vẫn phải được giữ lại trong Durable Notes.

test_short_term.py — Test 1: Sliding Compactionpytest
def test_sliding_compaction_preserves_durable_constraint():
    memory = ShortTermMemory(strategy="sliding", max_recent_messages=4)
    # Thêm 1 constraint quan trọng trước
    memory.add("user", "Constraint: REVIEW-DEADLINE-1600 is Friday at 16:00...")
    # Thêm 10 turn chat rác sau đó → kích hoạt compaction
    for i in range(10):
        memory.add("user", f"filler turn {i}")
    text = memory.render()
    # PASS nếu: constraint vẫn còn trong output SAU khi compaction xảy ra
    assert "REVIEW-DEADLINE-1600" in text
    assert "Friday" in text
    assert "16:00" in text
    assert memory.compactions > 0  # Phải xảy ra ít nhất 1 lần compaction

Bất kỳ keyword nào bị mất sau khi các turn rác được thêm vào❌ FAIL
compactions == 0 (chưa bao giờ compact)❌ FAIL

def test_buffer_does_not_compact():

📥 Cách Đưa Dữ Liệu Vào Từng Loại Memory

4 tầng nhớ được nạp dữ liệu bằng các cơ chế hoàn toàn khác nhau. Short-Term nạp trực tiếp từ code Python. Ba tầng còn lại đều đi qua Zep Cloud API và cần chạy docker compose run --rm app python -m src.seed một lần trước.

💬 Short-Term Memory — Nạp trực tiếp bằng Python In-Memory / Không cần Zep

Ai đưa dữ liệu vào? Code Python gọi memory.add(role, content) mỗi khi có 1 turn chat mới. Không đi qua mạng, không cần API key, lưu hoàn toàn trong RAM.

src/short_term.py — Cách nạp dữ liệuPython local
# 1. Khởi tạo bộ nhớ short-term
memory = ShortTermMemory(
    strategy="sliding",       # Chế độ: sliding window
    max_recent_messages=6,  # Giữ tối đa 6 turn gần nhất
    pressure_tokens=500     # Nếu vượt 500 token → compact
)

# 2. Thêm từng turn chat vào (tự động compact nếu quá đầy)
memory.add("user", "Constraint: HOLD-ALPHA-0900 standup lúc 9:00")
memory.add("assistant", "Đã ghi nhận.")
memory.add("user", "Filler message không quan trọng")
# ... thêm nhiều lần → khi đủ áp lực → compact() tự chạy

# 3. Khi compact() chạy:
#   - Messages cũ → extract_durable_notes() → lưu vào durable_notes
#   - Constraint, deadline, must → LUÔN được giữ lại
#   - Messages bình thường → bị xóa, chỉ giữ 6 cái mới nhất

# 4. Render ra text để đưa vào context
text = memory.render()
# Output: <SESSION_SUMMARY>...</SESSION_SUMMARY>
#         <DURABLE_NOTES>- user: Constraint: HOLD-ALPHA-0900...</DURABLE_NOTES>
#         <RECENT_TURNS>...6 turns gần nhất...</RECENT_TURNS>
📌 Dữ liệu durable được giữ lại khi:
  • Nội dung chứa từ: constraint, deadline, decision, must, todo, preference
  • Hoặc có marker dạng HOLD-ALPHA-0900 (chữ hoa, có gạch ngang, >= 6 ký tự)

📓 Episodic Memory — Zep lưu raw episodes từ chat Zep User Episodes / Tự động

Ai đưa dữ liệu vào? Cùng lúc với Long-Term, khi seed gửi messages lên thread của user, Zep đồng thời lưu các đoạn chat thô thành Episodes — đặc biệt là các reflection, root cause analysis, kết quả debug.

// seed.py gọi:

📌 Sự khác biệt Long-Term vs Episodic:
  • Long-Term: Zep trích xuất facts ngắn gọn từ chat ("Minh likes Python")
  • Episodic: Zep lưu đoạn chat thô để tìm kiếm lại bằng vector search ("mình đã làm gì trong buổi debug async")
